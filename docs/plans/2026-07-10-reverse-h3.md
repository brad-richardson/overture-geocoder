# Reverse Geocoding: H3 Country Router + Exact Containment

Date: 2026-07-10
Branch: `reverse-h3-country-router`
Status: Exact-polygon router recommended; H3 retained only as a comparator

## Summary

Replace bbox-only country selection with a small exact-geometry router:

1. **Simplified country polygon components** in a compact R-tree/WKB artifact
2. **Exact point containment** after the R-tree bbox prefilter
3. **HEAD fallback** for zero/multiple matches or a missing/corrupt router
4. **Materialized parent hierarchy** via official division relationships

H3 res3 remains a possible acceleration layer, but measurements do not justify
making it a production dependency or source of truth yet.

## 2026-07-11 experiment outcome

The aggregate country bboxes are not a viable durable router. Against 980,494
real division centroids and 219 real country bboxes, 91.34% of points matched
multiple country bboxes. The smallest-area country was wrong for 37.63% of all
points (40.90% of ambiguous points), and 0.353% of rows were not contained by
their own aggregate country bbox. This centroid sample is biased, but the
failure rate is large enough to reject bbox heuristics categorically.

On 177 real Natural Earth low-resolution country polygons and 20,000 seeded
global points, a direct normalized-WKB STRtree lookup took 7.65 microseconds per
query in Python. H3 res2 plus exact boundary fallback took 3.25 microseconds and
res3 took 1.75 microseconds; both matched direct containment for all sampled
points. Compact deduplicated artifact estimates were about 158 KB direct,
189 KB H3 res2, and 316 KB H3 res3. The prototype's repeated-WKB JSON layout was
13.5 MB/43.4 MB and must never be promoted.

The simpler direct artifact is therefore the next production candidate. Repeat
the size/correctness benchmark with the pinned Overture country polygons and in
the actual worker before deciding whether H3's few-microsecond acceleration is
worth its build, versioning, and WASM complexity.

## Current Architecture

- `select_reverse_shards()` in stac.rs: iterates reverse-collection bboxes; an
  unambiguous match selects a country shard, while zero or multiple matches
  fall back to HEAD. IP country does not resolve geometric ambiguity.
- `Database::reverse_geocode()`: R*Tree prefilter, window keeps 8 smallest per subtype, dedup gers_id, priority subtype priority over area, centroid haversine tie-break factor 4x, hierarchy inferred smallest per subtype

Issues F5/F14:
- Country bboxes union of components → RU/US with parts both sides dateline → [-180,180] width → contains every lon → forces IP fallback
- distance_to_bbox didn't handle min_lon > max_lon (Fiji)
- Overlapping US/CA ambiguous
- No exact polygon
- Hierarchy inferred not materialized

PR #43 fixed subtype priority; this PR builds on it.

## Improvements Shipped

### 1. Antimeridian-aware helpers (stac.rs)

```
normalize_lon: while >180 -=360, <-180 +=360
bbox_contains: lat in [min_lat,max_lat], if min<=max: lon in [min,max] else lon>=min || lon<=max
bbox_area_deg2: width = crossing? (180-min)+(max+180) : max-min
```

### 2. Smallest-area overlapping heuristic

Collect all containing bboxes with area, sort ascending, return smallest.

- JP 832 vs RU world 14760 → JP wins even without CF country (Tokyo fix)
- CA 3738 vs US 1534 → US wins

Original fallback: 0 containing → CF country → HEAD, 1 → that, N → smallest area. The guardrail below supersedes the `N` case.

### Immediate overlap guardrail after deployment

Live smoke testing exposed the limit of smallest-area routing: Boston was inside both CA (`[-141.0026607, 41.6765597, -52.6193663, 83.1370864]`) and an aggregate US bbox inflated by disconnected territories, so the smaller CA bbox won and reverse returned Canada. The production guardrail now sends every multiple-bbox match to the global HEAD reverse shard, regardless of `CF-IPCountry`. Request coordinates remain authoritative and stale/VPN IP metadata cannot redirect a query to a geometrically wrong country shard.

The limitation is explicit: HEAD fallback can return a less specific result than
a country shard. A compact exact polygon router is the durable fix.

### 3. distance_to_bbox fixed for wrapping

Closest lon chooses nearer edge when point in gap (max,min).

### 4. Exact containment scaffold (geocoder-core)

- has_wkb: OnceCell probing SELECT wkb LIMIT 0
- New SQL REVERSE_GEOCODE_*_WKB selecting wkb
- ReverseDivisionRow.wkb Option<Vec<u8>>
- Pure-Rust WKB parser: Polygon(3)+MultiPolygon(6), handles Z/M via %1000, little/big endian, ray-cast even-odd holes excluded
- After bbox prefilter filter out rows where point_in_wkb==false (parse fail → conservative true)

Future build can add wkb BLOB to divisions_reverse simplified tolerance 0.0005° (~50m).

## H3 vs S2 Tradeoffs

| Aspect | H3 (hex) | S2 (quad) |
|---|---|---|
| Cell shape | Hex 6 neighbors uniform | Quad 4 children Hilbert |
| Projection | Icosahedron area-preserving-ish | Cube better near poles |
| Wasm | h3 C-binding fails wasm, h3o pure Rust works | s2 pure Rust works but larger |
| Res levels | 0:122 cells 1107km, 1:842, 2:5882 avg158km, 3:41162 avg60km, 4:288k avg22km | L6 ~1°, L10 ~0.1°, L12 ~0.02° |
| Storage | 64-bit int | 64-bit cell ID |
| Fit | Good: res2 ~5882 cells global, country few to hundreds, boundary ~20% | Similar hex better adjacency |

Comparator choice: H3 res2-3. Production choice: direct exact polygon routing
unless the pinned Overture/worker benchmark exceeds an explicit size or CPU
budget.

- res2 5882 cells avg 250k km2 country-scale
- res3 41162 cells avg 60km edge ~10k km2 more precise
- Boundary cells need polygon exact check; interior direct mapping.

Wasm: use h3o crate pure Rust; Python build uses h3-py C fine.

Why not S2: S2 spherical-acc accurate vs H3 planar-ish but for country level negligible. Hex uniform adjacency better for irregular borders.

## Build Pipeline Design

### Phase 0: compact exact country router (recommended first)

Extract official country `division_area` polygon components, normalize/split
antimeridian components offline, simplify with topology preservation, and write
one deduplicated WKB record plus an R-tree bbox entry per component. The worker
bbox-prefilters and then runs exact containment. Zero/multiple matches or a
missing/corrupt artifact fall back to HEAD.

### Phase 1: Country H3 comparator (Python offline)

Script `scripts/build_country_h3_index.py`:

1. Input division-area parquet filtered subtype=country
2. For each country load WKB via shapely, merge unary_union, make_valid, simplify optional
3. Enumerate the complete H3 grid at res2/3 (5,882/41,162 cells) using h3-py 3.x or 4.x APIs
4. Convert each cell boundary to a Shapely polygon and query a spatial index of country polygons
5. Mark a cell interior only when exactly one country covers the complete cell; any intersecting-but-not-covered coast, hole, or border cell is a boundary candidate, including one-country coast cells
6. Unwrap cell and country rings at the antimeridian and index copies shifted by ±360°, avoiding the planar `179 → -179` long-edge failure
7. For boundary output, retain candidate countries and simplified country WKB for exact query-time containment

The script now uses actual intersection/coverage rather than center-point polyfill. It remains an offline experiment: boundary WKB is currently the complete simplified country geometry repeated per cell, not clipped/deduplicated, so its JSON size is an intentionally conservative upper bound and is not the proposed production layout. Proposed output SQLite `country_h3.db`: `h3_cells(cell PK,country,is_boundary)` plus deduplicated or cell-clipped `boundary_polys`, or equivalent compact binary data. The classifier unwraps antimeridian geometry, but the stored WKB keeps the source coordinate convention; a production consumer must normalize the query/polygon consistently or rely on pre-split components before exact ray casting.

`--compare-resolutions 2,3 [--report report.json]` reports global cells, land-intersecting cells, interior/boundary counts, boundary percentage, and estimated compact JSON bytes without writing index artifacts. A two-rectangle synthetic validation produced:

| Resolution | Global | Land | Interior | Boundary | Boundary % | Compact JSON upper bound |
|---|---:|---:|---:|---:|---:|---:|
| 2 | 5,882 | 283 | 196 | 87 | 30.74% | 28.7 KB |
| 3 | 41,162 | 1,807 | 1,573 | 234 | 12.95% | 101.2 KB |

These are correctness/tooling checks, not world-country sizing results. Run the comparison against the target Overture division-area release before selecting a resolution.

### Phase 2: Reverse shards with WKB

Modify build_shards.py:

- Schema wkb BLOB optional
- Query division_area join to get simplified geometry per division: ST_SimplifyPreserveTopology(geom,0.0005)
- For antimeridian keep split rows each with its own simplified WKB component
- Store simplified WKB binary
- Size estimate Overture area 20k rows ×1-2KB=20-40MB total fleet vs current 10MB acceptable per shard +0-2MB under 128MB limit
- Optimization store WKB only for admin levels or where bbox area >> polygon area or centroid not inside

### Phase 3: Worker integration

- Load country_h3.db into isolate cache (like RouterDb)
- If H3 later clears an explicit benchmark: h3.latlng_to_cell(lat,lon,res=3)
  selects interior cells directly; boundary cells use the same deduplicated
  exact polygon artifact. Any miss/ambiguity/error falls back to HEAD, never a
  smallest-bbox or IP-country heuristic.
- Database::reverse_geocode exact containment using shard wkb as implemented

### Phase 4: Materialized Parent Hierarchy

Current hierarchy inferred smallest per subtype. Better use Overture parent_id or admin hierarchy.

- In DuckDB build join division → division_area parent chain via country,region or parent_gers_id if exists
- Store parent_gers_id in divisions_reverse
- Then hierarchy walk parent pointers
- Size extra 16-byte UUID per row ~300KB/shard

Future parent materialization deprecates area-based confidence → containment confidence (high if inside exact poly, medium if near edge)

## Wasm feasibility

An isolated local probe (not added to the workspace dependencies) compiled `h3o 0.10.0` and a `LatLng::to_cell(Resolution::Three)` export successfully with `cargo check --target wasm32-unknown-unknown`. A release `cdylib` containing that export was 86,163 bytes before wasm optimization. The repository already has the `wasm32-unknown-unknown` target installed.

This clears the basic target-compatibility blocker, but does not justify adding the dependency yet. Remaining evidence needed: incremental size in the real worker (rather than a standalone artifact), Cloudflare runtime smoke coverage, lookup/index decoding cost, and a benchmark against the existing bbox router. Keep `h3o` out of production until the country index layout and resolution are selected.

## Storage Estimates

- H3 global grid cardinality: res2 5,882 cells; res3 41,162 cells. Only land-intersecting cells need records.
- Interior routing entries should remain small (8-byte H3 plus compact country ID), but must be measured on actual Overture country geometry.
- Prototype JSON repeats full simplified WKB for every boundary cell and is an upper bound. Production should deduplicate each country polygon or clip per-cell before trusting size estimates.
- Reverse WKB addition: 20-40MB fleet per-country +0-2MB still <128MB worker limit
- RouterDb few MB + H3 DB separate or merged
- Total extra cache <5MB

## Migration Plan

1. Keep the shipped HEAD-on-ambiguity production guardrail.
2. Extract only the pinned release's official country polygon components.
3. Benchmark simplification tolerances, artifact bytes, cold decode/heap, exact
   lookup latency, and border/coast/antimeridian gold cases in the real worker.
4. Integrate the compact exact artifact if it meets budget.
5. Compare H3 res3 only if direct exact routing misses an explicit budget; do
   not promote the repeated-WKB prototype layout.
6. Long-term materialize the official parent hierarchy and deprecate inferred
   area confidence.
